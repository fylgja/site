faq:
  - question: Why does the error not show while I am still typing?
    answer: The error follows the :user-invalid pseudo-class, which only matches after
      the user has changed the field and moved on, or tried to submit the form. An
      empty required field is invalid from the start, and :user-invalid keeps that
      from being shown before the user has done anything.
  - question: Can I show a different message for each validation rule?
    answer: Not with CSS alone. The field-error-message class only knows the field is
      invalid, not why. Write one message that covers every rule, or read
      input.validity in a script and swap the message text.
  - question: How do I show an error from the server?
    answer: Render the field with aria-invalid="true" and the message shows straight
      away. Remove the attribute with a script once the user edits the value, or the
      error stays visible.
  - question: Can I hide the browser's own validation bubble?
    answer: Adding novalidate to the form removes the bubble, but also stops the
      browser from blocking an invalid submit, so you then need a script to do that.
      Keep the native behavior unless you have a reason to replace it.

A form field groups a label, a control, optional hint text, and an error message.
Validation comes from the browser itself: attributes like `required`, `type="email"`,
`minlength`, and `pattern` decide when the value is invalid. Fylgja base turns the
border red, and the `field-error-message` class from form extend reveals the
message, all without JavaScript.

## Usage

- Wrap the label, control, hint, and error in an element with the `field` class.
  The error is scoped to that wrapper, so it can sit anywhere inside it.
- Add the native validation attributes the value needs. The browser does the
  checking.
- Give the error message the `field-error-message` class. It stays hidden until the
  control matches `:user-invalid` or has `aria-invalid="true"`.
- Point `aria-errormessage` at the error and `aria-describedby` at the hint.

The message uses `visibility`, so its space stays reserved while hidden and the
layout does not jump when it appears.

## Anatomy

- **`.field`**: the wrapper that ties the error message to its control.
- **`<label>`**: names the control, linked with `for` and `id`.
- **Control**: any `<input>`, `<select>`, or `<textarea>` with validation attributes.
- **Hint** (optional): a `<small>` below the control with guidance that is always
  visible. Use it sparingly, for passwords and other inputs with rules the label
  cannot convey.
- **`.field-error-message`**: the message shown once the control is invalid.

## Accessibility

- Every control needs a visible `<label>`. A placeholder is not a label, since it
  disappears as soon as the user types.
- Link the hint with `aria-describedby` so it is read along with the label. Do not
  add the error to `aria-describedby` as well, since screen readers would then
  read the hidden message every time.
- `aria-errormessage` links the error to the control. Screen reader support for it
  is still uneven, but on submit the browser also announces its own validation
  message and moves focus to the first invalid field.
- Write the error as a fix, such as "Enter an email address", not just "Invalid".
- Do not rely on the red border alone. The message text carries the meaning for
  users who cannot tell the colors apart.

## Variants

### Several rules

Combine `required`, `minlength`, `maxlength`, and `pattern` on one control. Since the
message cannot tell which rule failed, describe all of them in it.
